# 文献卡片与 Wiki：Skill 驱动、Markdown 作为正文主存储

## 结论和范围

建议一个项目级 skill、两种工作模式：卡片提炼一篇论文的关键证据，Wiki 跨材料综合、质疑和拓展。Agent 直接创建或修改 Markdown，不返回正文 JSON 让平台转写。平台保留目录浏览、搜索、任务进度、索引、历史和人工审核；数据库可以保存可重建索引，但不能再作为正文的另一写入源。

本文件为方案，不执行 skill 安装、业务代码修改、数据迁移或服务重启。2026-11-10，paper_analyze，基线 3ce8a9a，依赖已安装，工作树起始干净。现有证据见 plans/literature-markdown/notes.md。

## 现状与必须解决的问题

当前专用任务：材料快照 → 固定提示词 → 只读 CLI → output.json → 协议字段校验 → 数据库版本 → 平台生成 Markdown。聊天入口则使用平台工具提交结构化对象，也经过知识存储写入。两者均不是纯文件写作。

卡片目前九个固定栏目，部分字段藏在单行 metadata JSON 内；手工调整栏目名称或顺序可能解析失败。Wiki 正文较自由，但仍依赖已登记对象和版本。当前同步从已有数据库记录寻找文件，不会自动识别任意新增 Markdown。

因此不能只删 JSON 输出要求：否则新文件可能不显示，旧数据库内容可能被重新发布覆盖文件。需要同时改生成、发现、读取、编辑、历史和审核链路。JSON 不是所有失败的根因；本方案减少正文序列化和双向同步，不承诺消除模型失败、权限问题或文件冲突。

## 内容设计

### 卡片：一篇论文一个默认主卡片

以 source_id 去重：重复生成更新原卡片，保留用户补充；同论文不同项目可以有各自卡片。正文推荐 300–600 中文字，复杂论文可超出，不为字数删关键条件。只读摘要时标记“仅摘要”，不能伪装已阅读全文。

只保留四部分：一句话概括；关键方法；关键证据与局限；与本项目的关系。关键数字必须带数据集、评价条件及页码/表号；缺失信息写“原文未说明／未核实”。未关联研究问题时最后一节说明尚未判断相关性，不能编造研究价值。

示例（占位符不是真实论文事实）：

```markdown
---
id: card-example
kind: literature-card
source_id: source-example
---
# 论文标题

> 作者 · 年份 · 发表位置 · DOI/原文链接
> 阅读范围：全文；原文：[PDF](相对路径.pdf)

## 一句话概括
这篇论文针对什么问题，采用什么办法，得到什么主要结论。

## 关键方法
- 与已有方法相比最关键的设计及适用前提。（§3）

## 关键证据与局限
- 作者结果：指标、数据集、比较条件与原文位置。（表 2，PDF 第 6 页）
- 局限：作者明确指出的限制；自己的判断另行标明。

## 与本项目的关系
可借鉴的具体设计，及还需要验证什么。
```

推荐只强制 id、kind、source_id 三个简单 YAML 字段；标题来自一级标题，标签和阅读范围可选。时间、hash、审核状态由平台侧记录，不要求模型计算。来源链接和位置是正文证据，不靠隐藏大对象。

### Wiki：围绕一个问题组织知识

不是卡片摘要拼接。允许引用卡片、原论文、实验及经授权引入的外部来源；记录共识、矛盾、成立条件和研究空白。拓展明确区分“有来源的事实”“综合判断”“待验证假设”。默认只基于当前项目；需要检索外部资料时按用户授权和运行权限处理，新增来源必须可追踪。

推荐正文：核心问题与当前结论、证据与比较、分歧与适用条件、拓展与待验证问题、来源。栏目可调整，不硬编码解析顺序。

```markdown
---
id: wiki-example
kind: wiki-page
---
# 一个研究主题

## 核心问题与当前结论
给出有条件的判断，而非泛泛介绍。

## 证据与比较
比较 [论文 A](../literature/cards/card-a.md) 与
[论文 B](../literature/cards/card-b.md) 的问题设定、条件和证据。

## 分歧与适用条件
哪些结论不能直接比较，为什么。

## 拓展与待验证问题
- 假设：……
- 依据：……
- 验证方式：……

## 来源
- [论文 A](../literature/cards/card-a.md)：支撑哪条判断，原文位置。
```

优先标准相对 Markdown 链接；未来可额外支持 wikilinks，不在首版引入专用语法。引用来源被修改时平台按源文件 hash 提醒可能需要复核，不阻断正文阅读。自动提示只表明来源变化，不证明语义已失效。

## Skill 组织和实际加载

建议位置 `.agents/skills/trash-literature-knowledge/`：

- SKILL.md：触发说明、卡片/Wiki 模式、阅读与证据纪律、更新和交付约定。
- references/card.md：精简卡片要求与示例。
- references/wiki.md：综合、分歧、拓展及链接规则。
- assets/card.md、assets/wiki.md：最小模板；只有模板确有复用需要才创建。

一个 skill 保持共同证据规则一致，两模式分别读相关参考，避免加载所有资料。skill 是写作规则，不代替平台文件发现和权限实现。不修改全局 Codex 配置。

运行时必须显式读取固定版本的 skill 文件，任务记录 skill 名称、内容 hash 和模式。不要依赖“已经安装所以必然使用”。项目论文工作区不是仓库根目录：生成任务需要把受控 skill 副本或可读路径传入上下文，并告知实际输出根目录；聊天 Agent 同样显式接入。

输入包括项目研究问题、目标论文路径或可读提取文本、现有卡片/Wiki、目标路径和本轮要求。可以继续使用内部任务 JSON 传控制参数，但正文必须由 Agent 写 .md。CLI stdout 只用于进度和说明，不再是正文输出协议。

Skill 执行：确认范围 → 读取材料与现有目标 → 提炼或综合 → 直接写 Markdown → 回读确认文件存在、链接和证据位置 → 汇报实际路径及未核实项。资料内指令不是用户授权；不自动安装、运行实验、联网、删文件或审核。

## 文件与平台职责

继续沿用现有目录，避免无必要迁移根路径：

```text
<论文项目根目录>/
  literature/cards/<稳定ID>.md
  wiki/<稳定ID>.md
  .trash/knowledge-history/   # 历史和旧版本兼容
```

ID 与标题解耦；改标题不改 ID。旧文件名和 ID 尽量保留，相对路径保持稳定。禁止把开发仓库和论文项目根目录混用。

平台扫描两个目录，识别新增文件和改动；提供显式刷新，watcher 只负责及时性，启动扫描和定期补扫负责漏事件恢复。仅索引受限目录，校验真实路径与符号链接，防止跨项目访问。每文件限制大小和文本编码，发现重复 ID、缺失字段、坏链接时逐文件提示，不能让一篇坏文件导致整页不可用。无 frontmatter 的普通 .md 仍可在文件模块查看，但不自动猜成正式卡片。

读取和预览直接读取文件；SQLite 保存 id、kind、path、title、source_id、hash、mtime、索引错误等派生信息，可从文件重建。允许 UI 与 API 继续使用 JSON 传列表和任务状态，取消的是“模型交正文 JSON → 平台排版写文件”这条链路。

新增文件在完整写入后才发布：同目录临时 .md.tmp，完成后原子替换；临时文件不入索引。已有文件更新先检查开始时 hash，再提交修改；用户同时编辑则保留候选文件并提示冲突，不覆盖用户内容。Skill 自觉回读不足以提供并发保证，应由受控文件写入工具或写作运行器实现校验和原子替换，工具只提交 Markdown 字节及目标路径，不重新拼正文。

读写沙箱应仅覆盖必要的知识目录；当前专用知识任务只读权限必须调整。直接写入一旦扩展权限，平台工具的只读/写入检查便不再能单独保护文件，聊天入口必须同步限制路径。普通 shell 直写无法完全保证所有写入都走冲突检查；首版建议任务先在隔离工作目录写 Markdown，再由受控文件操作原样提交最终目录。Agent 仍负责生成 Markdown，平台不做 JSON 转文档。

历史为文件快照加变更来源、hash 和时间；审核记录绑定 id 与 hash，正文改变立即变为待复核。Agent 无权自行接受审核。旧版本审核不能通过重新生成正文覆盖当前文件。删除先走可恢复回收站，首版不自动清理。

## 两个入口保持一致

卡片/Wiki 的生成按钮与 Agent 对话调用同一 skill 和同一文件目录。按钮只设置模式、输入和目标文件；对话可先讨论再写，用户只问问题时不自动生成文件。专用任务只有目标文件写入并索引成功才显示完成；写入成功而索引失败显示“文件已保存，展示待恢复”，禁止误报生成失败后无脑重试。

旧 project_tool.py 的卡片/Wiki write 应弃用或只返回新写法指引，不继续让模型走结构化正文。实验结果仍沿用现有结构化链路，本次不改。新旧入口必须有模式开关，防止一个项目被两种正文写入源同时管理。

## 迁移与回滚

1. 只读盘点每项目卡片/Wiki 数量、路径、hash、数据库版本和引用关系，列出缺失及冲突，不直接覆盖。
2. 在独立备份目录保留原 Markdown、全部历史及必要数据库备份，建立旧 ID 到新路径映射和迁移清单。
3. 将旧 metadata JSON 拆成少量 frontmatter 和可读正文，卡片按精简规则生成候选；原九栏目中的额外信息保留在历史/原始备份，未经确认不丢弃。机器转换与模型提炼分开，后者不能当无损迁移。
4. 使用实际副本验证显示、引用、历史、冲突和索引重建；本轮只规划，不执行验证。
5. 每项目切换文件主存储模式并禁用旧 reconcile/publish 正文写入，再启用新扫描和生成入口；切换期间暂停该项目知识写入。
6. 核对数量、文件 hash、可追踪链接和历史后标记迁移完成。失败保留所有文件和清单，不自动二次迁移。
7. 回滚前保存切换后的所有新增/修改文件；恢复旧模式不能直接用旧数据库覆盖新文件，先对照清单合并新增内容。

## 改动范围及分期

P0：项目级 skill；文件识别/列表/预览；新知识生成任务直接写 Markdown；聊天技能接入；原子提交与冲突保留；同项目新旧模式隔离；已有数据备份和迁移预览。确保从两种入口生成的真实文件都能展示。

P1：原有编辑器改读写文件；搜索和来源变化提醒；hash 绑定人工审核；历史对比、重建索引及可恢复回滚。旧项目在这些兼容能力完成前不全量切换。

P2：知识关系图、批量自动拓展、Obsidian 特有语法、自动联网更新。首版不做，避免偏离简洁可靠的文件写作。

涉及 `.agents/skills/`、apps/server/src/knowledge-agent.ts、project-chat-tools.ts、code-agent.ts、knowledge.ts、packages/storage/src/knowledge.ts 与 knowledge-markdown.ts，以及知识页面相关组件。先通过搜索确认所有调用点，再决定拆分新的文件索引服务；不直接推翻所有存储代码。实验结构化数据与其他功能保留。

## 未来验收（本轮未执行）

- 一篇论文生成一个精简主卡片，重复生成不重复建卡，标题变化不丢身份。
- 新文件无需 knowledge.write 正文 JSON 即出现在列表；按钮和聊天写入同一目录。
- 至少两篇材料能形成有来源、有比较、有待验证假设的 Wiki；未联网不捏造外部文献。
- 缺失全文、条件不一致、找不到证据时明确披露。
- 临时文件、截断输出、取消任务不发布半成品；冲突保留双方内容。
- 一篇非法文件不阻断其他页面；删除数据库派生索引后可从文件重建。
- 来源变化触发提醒，人工审核随正文 hash 失效；旧历史仍可读。
- 迁移前后原始内容有可恢复备份，回滚保留切换后新增内容。
- 检查必要权限和跨项目目录边界；重启后任务状态可恢复解释。
